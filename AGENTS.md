# Правила разработки для агентов

## Перед изменением

- Проверьте `git status -sb`, `git rev-parse HEAD` и применимые `AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`. Сохраните чужие изменения. Прочитайте `README.md`, `composer.json`, `Makefile`, `.github/workflows/CI.yml` и относящиеся к задаче исходники и тесты.
- `Roadmap.md` — единая очередь этапов; `Tasks.md` — зависимости и проверяемая приёмка. Перед нетривиальной реализацией обновите оба файла и создайте PRD по `PRD/TEMPLATE.md`. Запишите исходный SHA и проверенные факты отдельно от гипотез.
- Для нетривиальной реализации требуется независимое ревью PRD **до изменения исполняемого кода** и независимое ревью полного diff **после реализации**. Сохраните проверяемое заключение, предмет ревью, SHA или диапазон diff и разбор замечаний в `PRD/reviews/`. Самопроверка и зелёный CI не заменяют независимое ревью. Если рецензента нет, оставьте gate открытым и передайте локальную ветку на ревью; draft PR допустим после изоляции CI. Не называйте открытый gate пройденным.

## Совместимость и безопасность

- Сохраняйте публичные функции `credentials()`, `token()`, `token_with_client()`, интерфейсы `Credentials` и `Token`, трёхаргументный конструктор `Token\FromGateway`, форматы `asKeyValue()` и `asString()`, а также наблюдаемую отложенность, кеширование и повтор после ошибки. Изменение этого контракта требует отдельного решения владельца и плана версии.
- Не меняйте диапазон PHP, ограничения Composer, поддерживаемые версии `vetmanager-url`/Guzzle, CI secrets и текст публичного README в рамках инфраструктурной работы без обоснованного решения владельца. Расхождение README, CI и Composer по PHP — открытый вопрос `Tasks.md`, не повод молча исправить одно из них.
- Пока матрица PHP не подтверждена, применяйте синтаксис не новее PHP 7.3 в `src/` и тестах. Сохраняйте PSR-12, существующие пространства имён и структуру `tests/unit/`, `tests/integration/`. Новое поведение сопровождайте офлайн unit или контрактными тестами с Guzzle MockHandler.
- Не переносите `.env`, реальные логины, пароли, токены и ответы API в Git, PRD, лог или вывод ревью. Сетевую интеграцию запускайте только с явно тестовым окружением и разрешёнными тестовыми данными; production не использовать.

## Проверки и фиксация результата

- Документы: проверьте ссылки, статусы и зависимости, `git diff --cached --check` для staged правок (или `git diff --check` для unstaged), `git diff --cached --stat` и полный diff. Для кодовых изменений сначала выясните работоспособность локального Docker/Composer, затем выполните `make all PHP_VERSION=8.0` и необходимые варианты PHP/URL из `Tasks.md`. `make integration` — отдельный gate с подтверждённым тестовым окружением; результат автоматического CI подтверждает только офлайн-проверки.
- В PRD или задаче запишите **точные команды, exit codes, версии PHP/Composer и URL, количество тестов, SHA и ограничения**. Не выдавайте непроведённые проверки за успешные. Результат CI относится только к проверенному SHA.
- Перед коммитом разберите замечания независимого ревью. Сообщение коммита кратко объясняет цель; добавьте `Co-Authored-By: Codex CLI <noreply@openai.com>`. Push, PR, merge и deploy выполняйте лишь в рамках поручения и полномочий. Не используйте reset с потерей данных, amend или force-push без отдельного разрешения.

## Актуальная точка входа

Проверенный исходный срез и нерешённые вопросы приведены в `PRD/agent-development-foundation.md`. Следующий исполнитель начинает с `Roadmap.md` и `Tasks.md`; будущие статусы обновляются только по фактическим результатам.
