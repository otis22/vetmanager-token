## Подтверждённая отправная точка

- Публичные функции `credentials(string, string, string): Credentials`, `token(Credentials, string): Token`, `token_with_client(Credentials, Url, ClientInterface): Token` объявлены в `src/functions.php`. `token()` возвращает `Token\FromGateway` с ленивым поиском URL через Billing и двумя стандартными клиентами Guzzle; `token_with_client()` возвращает `Token\FromResponse` с подготовленным URL и переданным клиентом. Трёхаргументный `Token\FromGateway` сохранён для выпущенного API 0.2.2.
- Запрос к `/token_auth.php` — POST с `form_params` из `Credentials::asKeyValue()`. Создание объекта токена не выполняет запрос; первый `asString()` получает токен, успешное значение кешируется в объекте. `Url\Lazy` кеширует только успешно разрешённый URL. После неудачного Billing или token-запроса следующий `asString()` повторяет попытку; не предполагается автоматический повтор внутри одного вызова.
- `composer.json` не объявляет `php` constraint. README утверждает PHP 8.0/8.1, по умолчанию Makefile выбирает 8.0, а CI проверяет 7.3/7.4/8.0 плюс URL 0.3.2/1.1.0 на 7.4/8.0. Это **не подтверждает** единую поддерживаемую матрицу. URL constraint: `~0.1 || ^1.1`; Guzzle: `^7.1`. `composer.lock` отслеживается Git.
- `vetmanager-rest-api` на указанном `main` требует `otis22/vetmanager-token:^0.2.0`. Поэтому совместимость существующего 0.2.x API и поведения — условие любых минорных изменений.
- В `tests/unit/` есть офлайн тесты MockHandler для URL, запросов, кеша и повторов. `tests/integration/` обращается к внешней клинике. Начиная с [`288fb5b`](https://github.com/otis22/vetmanager-token/commit/288fb5b758152897f37cf77b4df7950087db26fd), push/PR запускают только офлайн CI; интеграция вынесена в ручной workflow с отдельным окружением и проверкой подтверждения тестовой клиники. Для этого SHA [PR CI](https://github.com/otis22/vetmanager-token/actions/runs/40068350175) и [push CI](https://github.com/otis22/vetmanager-token/actions/runs/40068298510) завершились успешно (по 7 заданий). На том исходном этапе назначение клиники и настройка окружения не были подтверждены, интеграция не запускалась; локальный `make all PHP_VERSION=8.0` остановился при сборке Docker с exit 130. Последующие результаты приведены ниже.

## Офлайн-проверка 2026-10-24

- Штатный `make all PHP_VERSION=7.3`, `7.4` и `8.0` прошёл на PHP 7.3.33/7.4.33/8.0.30 с Composer 2.10.3: в каждой ячейке 44 теста, 145 assertions, 3 skipped, покрытие 94.51%. Исправлен только инструментарий Docker; публичный код и ограничения зависимостей не менялись.
- Чистое `composer update --prefer-lowest --prefer-stable` на PHP 7.3 и 8.0 разрешилось с URL 0.3.2 и Guzzle 7.15.2. Офлайн unit прошёл в обеих ячейках (44/145/3, покрытие 93.93%), но старый минимальный PHPStan не проходит: на 7.3 даёт 20 ошибок анализа, на 8.0 падает внутри своей зависимости. Это открытый риск минимального набора dev-зависимостей.
- Чистое production-разрешение `composer update --no-dev` прошло: PHP 7.3 выбрал URL 0.3.2 / Guzzle 7.16.0, PHP 8.0 — URL 1.1.1 / Guzzle 7.16.0. Autoload и создание фасада `token()` без сети прошли в обеих ячейках. Интеграционное поведение не проверено.
- Подробные команды, ограничения и заключения ревью — в `PRD/offline-compatibility-gaps.md`. Billing через сам фасад `token()` остаётся открытым C2: клиенты создаются внутри фасада, переносимый MockHandler без изменения production-кода недоступен.

Решение владельца от 2026-10-24: для 0.2.x сохранить PHP 7.3, 7.4 и 8.0; PHP 8.1 не заявлять до отдельной проверки. Ручная интеграция разрешена только с изолированной devtr6. Новые проверки и их ограничения фиксируются в `PRD/php-matrix-finalization.md`; выпуск R1 остаётся отдельным решением.
